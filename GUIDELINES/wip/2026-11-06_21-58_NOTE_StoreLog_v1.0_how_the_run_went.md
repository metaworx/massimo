# NOTE StoreLog v1.0: how the run went

The run of Blocks 1 to 3 under `EXEC++` on 2026-11-06,
in the session the plan was handed to,
where the work went differently from the plan, a line each.

- **The branches**:
  `claude/store-d` holds Block 1,
  `claude/store-d-2` Block 2 and `claude/store-d-3` Block 3 with this NOTE,
  each stacked on the one before; nothing is pushed.
- **The size per event** is 643 bytes in the file for a state event of 421 bytes of JSON,
  its indexes included (`TestEventSize`);
  the plan's 0.4 KB was the JSON alone. docs/store.md and packaging/README.md
  state about 0.65 KB, 2 MB a day and 60 MB at 30 days for thirty devices.
- **AddEvent queues while no writer runs**, in the bounded buffer,
  rather than dropping: the writer starts in a goroutine of `Run`,
  and the first events of a connection may come before it.
  A second writer on one store refuses and logs it;
  `FlushEvents` gives up after ten seconds on a writer that stopped answering.
- **250 events may land in two transactions**:
  a read's flush takes everything pending at once; the test allows one to three,
  as the plan's "at most three" says.
- **serve waits for the server's run** (up to ten seconds) before it closes the store,
  so that the writer's last flush is not after `Close`;
  the plan took that wait for granted, and serve did not have it.
- **A Cube learns its row at every connection** while it has none, by serial,
  not only the plain settings-file Cube.
- **The ring answers an `id` cursor with an empty page**:
  its events have no ids, and paging stops there rather than looping.
- **The pytest Older test** stubs a full page of 200 first,
  since a page shorter than 200 ends the paging;
  the plan's page of three would have disabled Older at once.
- **The settings shots are 49 px taller**:
  the Users panel lists the guest the runner has created since stage (c),
  which the set had not shown yet.
- **The "Could not pin down" list** the handover named is not in the plan;
  nothing was left to settle from it.
