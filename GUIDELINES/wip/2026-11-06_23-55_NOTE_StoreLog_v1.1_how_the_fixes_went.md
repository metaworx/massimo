# NOTE StoreLog v1.1: how the fixes went

The run of Blocks 4 to 6 under `PLAN++` on 2026-11-06,
where the work went differently from the plan, a line each.

- **Block 4's figures**:
  a page takes 0.3 to 2 ms at 90,000 events of one Cube beside 10,000 of
  another, a page by time 7 ms (`TestEventsPageQuery`, logged);
  the 90,000 rows are one `INSERT … SELECT`, about a second,
  so the test runs in the gate, under `-race` too.
  A ninth shape, a time with a device, is tested beside the plan's eight.
- **The size per event** is 638 bytes with migration 0004's indexes, 643 before:
  docs/store.md's "about 640 bytes" and packaging/README.md's 0.65 KB stand,
  so Block 5 left packaging/README.md as it was.
- **The merges forward** do not name the plan's revision:
  `commit-msg.sh` refuses a message naming AP StoreLog v1.1 on a branch the
  merge has not brought it to yet.
  The merge of the store branch into the server branch had a CHANGELOG conflict,
  resolved with the server branch's wording and migration 0004.
- **Older waits for a new log**:
  `loadLog` marks the log loading,
  so an Older pressed while a new log loads cannot put its page on the new
  lines; the plan's generation alone did not cover that.
- **Rows of trimmed lines stayed in the view**, on `main` too:
  past the room the oldest lines left `logState.lines` and not the page.
  Fixed on the way, with a check in `test_log_answers`.
- **The regressions are proved**:
  `TestLogLastEvents` fails against the old `Run`,
  and `test_log_answers` against the old `log.js` at its Clear step,
  both run with the old file swapped in.
- **A pytest run hung for ten minutes**:
  `page.evaluate("loadLog()")` waits for the promise it returns,
  which the held request never settled; the test calls it without returning it.
