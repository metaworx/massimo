# NOTE Restart v1.0: how the run went

How `PLAN++` carried out Blocks 1 to 4 of AP Restart v1.0, where it went
differently from the plan.

1. **Block 2, `serveHTTP`.**
   The plan's Analysis said the stop waits for the restart's request,
   through `http.Server.Shutdown`.
   It did not: `Serve` returns as soon as Shutdown begins, and `runServe` did
   not wait for Shutdown, so the store could close under a request still
   being answered, its audit row included.
   Block 2 makes `serveHTTP` wait for its Shutdown, within the 5 s grace,
   with a bullet under Fixed.
   AP CleanStop (pull request 84, another session) carries the same hunk and
   bullet word for word, so the two merge cleanly.
2. **Block 2, the systemd detection.**
   The plan named `INVOCATION_ID`. Every process a service starts inherits
   it, such as the shells of a desktop terminal that runs as a user service,
   so a `serve` started there would have offered a restart nobody completes.
   A commit of its own, after Block 3, also asks `SYSTEMD_EXEC_PID` to name
   `serve` itself, or, before systemd 248, the parent to be PID 1.
3. **Block 3** has an end-to-end test beyond the plan's list: the built
   binary, a `POST`, exit status 75, the store closed with the audit row in it.
4. **A cleanup commit** rewraps the lines Blocks 1 to 3 wrote, for the
   reflow check's warnings.
5. **Not done:** the screenshots of Settings (`make ui-screenshots`) are not
   retaken, so the Software section's new line is not in them.
6. **Seen once:** one run of `go test -race` over `internal/server` and
   `cmd/massimo` together ended in `FAIL`, its output cut off by `tail`;
   eight runs since, alone and together, passed.
   The failing test is unknown.
