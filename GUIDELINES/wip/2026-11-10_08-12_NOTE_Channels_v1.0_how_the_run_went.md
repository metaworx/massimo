# NOTE Channels v1.0: how the run went

The `PLAN++` run of AP Channels v1.0 (`2026-11-10_07-28_AP_Channels_devel_nightly_flavours.md`),
2026-11-10, on the branch `claude/channels`: Blocks 1 to 9, one commit each,
`633fb92` to `864ffca`. Nothing pushed but the plan's registration (`3ba8205`).

## Where it went differently

- **The commits of Blocks 3 to 6 are `ci(pipeline):`**, not `ci(release):`
  as the plan proposed: `commit-msg.sh` reserves the component `release`
  for the release role (`chore(release):`).
- **`devel` is published by the push run of `main` alone.**
  Block 5's step said "on a push to `main` and on a tag";
  the release commit runs CI twice (the plan's Discussion), and its push run
  makes the devel build of the very commit the tag releases,
  so the tag's run releases the tag and nothing else.
- **Block 1 stopped for the rolling key**, as the gate said it would;
  the owner made it, and the other steps of the setup commands, during the run
  (checked read-only: the reviewer on `signing`, its admin bypass off,
  `RELEASE_BRANCH_DEPLOY_KEY` beside the release key,
  `signing-rolling` admitting `main`, the three rulesets, the write deploy key).
- **`store.SettingString` is exported** (Block 2), the server and the command
  line reading `update.channel`; the six callers in `internal/store` renamed.
- **The workflows were not linted with actionlint:** fetching it was refused
  as code from outside. Instead: the YAML parsed and every `needs` resolved;
  every `run:` script through `bash -n` and shellcheck;
  `meta`'s script run here for a tag, a push to `main`, and by hand
  (against the repository's real runs, with the name of a job that exists
  today); the sign and rolling checks run on `mkmanifest`'s manifests.
- **`publish.sh` now skips non-`v` tags** (Block 5, not foreseen):
  `channel_of` would have put `release/devel`'s packages in the `stable` suite.
- **The apt index asset was also built from the real releases**
  (`--releases 1`, a throwaway key): its URLs name the release files.
- **Block 8 filled the partial `docs/fragments/_build.md` by hand** in README.md
  and `packaging/site/index.html`: `sync-docs.sh` in a worktree, whose guidelines
  submodule is empty, would rewrite AGENTS.md from nothing. The new line had to
  be broken where the generator's reflow breaks it before `--check` was clean.
- **Block 9 numbers its item 19**, after 18, the highest the roadmap ever used.

## What only GitHub can show

1. **Blocks 3, 4 and 7** at the next `make release-alpha`:
   the tag's full suite, then `sign` waiting for the owner's approval,
   `release/alpha` made by the deploy key, and `massimo-apt-index.tar.gz`
   on the release (`apt-build` may ask for a second approval).
   Then `git push origin --delete alpha`.
2. **Block 5** at the first push to `main` after the merge:
   `release/devel` created; at the second, replaced in place.
   Two open questions it answers: whether `gh release` handles a tag with a
   `/` throughout, and whether `GITHUB_TOKEN` may move a tag over commits that
   change `.github/workflows/` (GitHub refuses it a branch; tags are believed
   exempt). Then `massimo update -check -channel devel` on a box.
3. **Block 6** the first night, or `gh workflow run release.yml --ref main`:
   `release/nightly` from the newest commit whose "All tests passed" succeeded.
4. **The notes' `[Unreleased]`** appear once the guidelines submodule is at
   v4.54.0 or later (`changelog.sh preview`); until then the notes say so.
