# NOTE Channels v1.0: version tags only

For AP Channels v1.0 (`2026-11-10_07-28_AP_Channels_devel_nightly_flavours.md`),
after the NOTE "after the merge".

Run 42787778183, the push to `main` of
"ci(pipeline): A rolling build's manifest is replaced after its files",
failed in both Debian package jobs:
the first `release/devel` tag, made at 08:49 UTC, was a tag like any other to
`git describe --tags`, which named that commit `release/devel-1-g…`,
and `make packages` could not name a package by that.
Every push and pull request whose history held the tag failed the same way,
and `make release-alpha`'s and `meta`'s exact-match checks could have named
`release/devel` instead of the version tag at the same commit.

The owner had it pushed straight to `main` (D23-A):
`fix(pipeline): Versions come from the v tags alone`,
`--match 'v[0-9]*'` in the Makefile's `VERSION`, in `make release-alpha`'s check
and in `meta`'s; `GUIDELINES/project/CI.md` v1.30.0 states the rule.
`FLAVOUR` and the rolling build's version had it already.

The lesson: a tag that is not a version must never reach `git describe`;
any new tag namespace needs the same look through every `describe`.
