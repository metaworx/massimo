## The finding

A checkout that holds an older copy of a rolling tag refuses `git fetch --tags`:
`! [rejected] release/devel -> release/devel (would clobber existing tag)`, exit 1.
Seen on 2026-11-10 in the main checkout while v0.13.0-alpha.1 was cut.
`make release-alpha` fetched with `--quiet`, which hides the rejected line,
and its `&&` chain covered only the next two statements,
so it ran on without `origin/main` and said
`main is not origin/main (); pull or push first`.

## The fix (owner, `EXEC+`, 2026-11-10)

- **D1-A:** `make release-alpha` fetches `main` and `refs/tags/v*` alone,
  all it reads.
  A `v` tag moved on origin is still refused.
  Not B, `--tags` with `+refs/tags/release/*` forced:
  the next tag namespace that moves breaks it again;
  not C, `--force --tags`: it moves a local `v` tag without a word.
- **D2-A:** a failed fetch stops it with its own message, naming the command.
- **D3-A:** recorded here, not in a plan of its own.
- **D4-A:** a pull request, not a push to `main`.

`GUIDELINES/project/CI.md` v1.34.0, section 6, states the rule.
CI fetches every tag forced already; `packaging/` and `tools/` fetch nothing.

The lesson extends "version tags only":
a tag that moves must reach no unforced fetch either.
A person's own `git fetch --tags` meets it too;
`git fetch --force origin 'refs/tags/release/*:refs/tags/release/*'`
brings a checkout's copies up to date.
