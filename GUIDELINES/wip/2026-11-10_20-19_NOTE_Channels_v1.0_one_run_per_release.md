# NOTE Channels v1.0: one run per release

For AP Channels v1.0 (`2026-11-10_07-28_AP_Channels_devel_nightly_flavours.md`),
after the NOTE "rolling tags and fetch".

## What v0.13.0-alpha.1 showed

The release commit of v0.13.0-alpha.1 ran the whole suite twice on 2026-11-10,
once for its push to `main` and once for its tag,
and neither run passed, so nothing was released:

- the tag's run failed on the Windows service,
  "Access is denied" replacing `massimo.exe`,
  which "Wait for the service's process before replacing massimo.exe" has fixed since;
- `main`'s run failed on the macOS job with exit code 141, a SIGPIPE:
  `massimo tls show | grep -q 'SHA256:'` under `pipefail`,
  `grep -q` exiting at its match while `massimo` still wrote.

Had `main`'s run passed,
it would have published a `devel` build whose version was exactly `v0.13.0-alpha.1`,
another binary than the alpha's under the same version.
The tag `v0.13.0-alpha.1` stays, without a release.

## Decisions (owner, 2026-11-10)

- **D27-C:** one gate job, What to test (Changed paths before),
  that every test job waits for:
  on a push to `main` of a commit whose summary opens with `chore(release): `
  it answers `suite=false`, and every job is skipped, All tests passed and Release too.
  The owner's proposal, as file_checksum_search keeps one run per release.
  Not A, the condition repeated on every job.
  Only an answer of `false` skips a job,
  since the required checks pass a skipped job and do not include All tests passed:
  a gate that fails lets every job run, and fails All tests passed.
- **D28-A:** through a pull request.
- **D29-A:** in the same pull request,
  a pipe into `grep` in ci.yml reads to the end (`grep … >/dev/null`),
  and `launchctl print | grep | head -3` takes `sed -n 1,3p`.
- **D30-A:** in the same pull request,
  a commit of its own that only moves the gate job to the top of ci.yml's jobs,
  as `style(pipeline):`; release.yml's jobs already stand in their columns' order.
  The order in which GitHub draws a column's jobs does not follow the file
  (release.yml's apt-build is drawn above Homebrew),
  so the graph shows the effect after the merge only.
- **D31-A:** the next release is `v0.13.0-alpha.2`, cut after the merge.
  Not B, `v0.13.1-alpha.1`.

The skipped jobs are still listed in the run, greyed:
GitHub lists every job of a run that starts,
and `on:` cannot filter by message;
`[skip ci]` would skip the tag's run too, which is the same commit.
