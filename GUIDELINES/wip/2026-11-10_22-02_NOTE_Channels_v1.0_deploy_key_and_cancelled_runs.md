# NOTE Channels v1.0: deploy key and cancelled runs

For AP Channels v1.0 (`2026-11-10_07-28_AP_Channels_devel_nightly_flavours.md`),
after the NOTE "version tags only".
The rules are in `GUIDELINES/project/CI.md`, section 6; this records the decisions.

## The rolling tag is pushed with a deploy key (D24-A)

On 2026-11-10 the second devel build failed in its Publish step:
`gh: Resource not accessible by integration (HTTP 403)`,
moving `release/devel` with `GITHUB_TOKEN`.
The token had moved the tag once,
and was refused after other merges had changed `main`'s workflow files
since the commit;
GitHub keeps the token from some reference updates that touch workflow files.

- **D24-A** (owner, `EXEC D24-A`): the tag is pushed over SSH with a deploy key,
  `ROLLING_TAG_DEPLOY_KEY` in the `signing-rolling` environment,
  as the release branch is with `RELEASE_BRANCH_DEPLOY_KEY`;
  without the key the token still tries.
  The owner made the key and the secret.

The fix went straight to `main`:
"fix(pipeline): The rolling tags are moved with a deploy key".
The first devel build after it moved `release/devel` so;
the nightly build started by hand the same day made `release/nightly`.

## "Cancelled" runs of main are accepted (D25-A)

GitHub keeps one waiting run per concurrency group.
A newer push to `main` cancels the older push's waiting run,
or its waiting `rolling` job,
and that run reads "cancelled" though nothing failed;
on 2026-11-10 the merge of #168 got no run of its own so,
its waiting run cancelled when the release commit of v0.13.0-alpha.2 queued.

- **D25-A:** accepted, and documented in CI.md:
  the newer commit holds the older one,
  and the nightly build goes by the job "All tests passed", not by the run;
  without the group, two builds' uploads could interleave.

## What to release stays apart from What to test (D32-A)

Asked whether What to release could be merged into ci.yml's gate job,
What to test:

- **D32-A:** it stays with the build,
  in release.yml then and in build.yml since AP ParallelBuild.
  The nightly build runs it without ci.yml;
  in the gate it would decide before the suite,
  and a rolling build's commit is only right at its end;
  and it needs the whole history and the Actions API,
  which would slow every pull request's gate.
  Not B, moved with a second copy for the nightly build;
  not C, an early check of a tag in the gate besides.
