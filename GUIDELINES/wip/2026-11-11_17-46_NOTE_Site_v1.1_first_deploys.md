# NOTE Site v1.1: first deploys

What the first deploys of the site showed,
the checks item 5 of NOTE Site v1.0 ("how the run went") left for them,
and the owner's decisions of 2026-11-11 (`EXEC D59-A and D60-A`).

1. **The untested parts ran.**
   v0.13.0-alpha.2's run made the plan's first deploy, the first with the
   docs, on 2026-11-10 at 19:55 UTC, from the apt repository it had just
   signed.
   Every run of `main` after it deployed from that release's
   `massimo-apt-index.tar.gz`, its pool downloaded by `pool.tsv`.
   v0.14.0-alpha.1's run did the same on 2026-11-11, and
   `/docs/channels.json` now names alpha, nightly, devel and main.
2. **Pages keeps the first deploy of a commit.**
   On 2026-11-11 the scheduled nightly build fired at 09:37 UTC on the
   release commit of v0.14.0-alpha.1, `main`'s head while the tag's run
   waited for its approval, and deployed at 09:41 with v0.13.0-alpha.2's
   index.
   The tag's run deployed the same commit at 09:46:
   deploy-pages logged `Created deployment for <commit>, ID: <commit>`
   and "Reported success!", GitHub marked the older deployment inactive,
   and Pages went on serving the 09:41 files.
   The Pages API takes the commit as the deployment's ID,
   and deploy-pages sets it from `GITHUB_SHA`, with no input to change it.
   A nightly build dispatched by hand on the next commit,
   "chore(aps): +OneLog v1.1", repaired the site at 10:19.
3. **The release commit's push to `main` played no part.**
   Its run skipped Release and Site, as every push of a release commit does;
   only the nightly build reached the site at that commit.
4. **The fix is AP ReleaseGates' D55-A**, merged with
   "ci(pipeline): One approval per release, the tap key behind it":
   a nightly build at a release commit builds and deploys nothing.
   That change carries its CHANGELOG fragment and CI.md section 6;
   the workflows need nothing more.
5. **D59-A:** `packaging/README.md`, "The site", says that a release commit
   is deployed by its tag's run alone, that Pages keeps the first deploy of
   a commit, and what a redeploy needs;
   it names v0.13.0-alpha.2 as the first release with the index,
   where it said that no release carried one.
   Not B, waiting for the plan's retirement:
   the section misled every reader until then.
6. **D60-A:** this NOTE records it on the plan whose checks it closes.
   Not B, AP ReleaseGates' record alone,
   which says nothing of the first deploys.
7. **Open, no change proposed:** a run of a later commit that reads the
   newest index just before a release's `apt-build` attaches the new one,
   and deploys after the release's site, would serve the old index again
   until the next deploy.
   The `pages` concurrency group orders the deploys, not what they hold;
   the window is about a minute, and it has not happened.
8. **For the owner:** item 7 of NOTE Site v1.0 came true.
   `docs/reports/windows-test-2026-11-05.md` is on the site under
   `/docs/main/` and `/docs/alpha/` since the first deploy.
9. **What is left of the plan:** none of its blocks.
   With its checks done, whether it retires is the owner's decision.
