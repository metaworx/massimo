# NOTE ZeroSlot v1.0: how the run went

How the run of [AP ZeroSlot v1.0](2026-11-14_13-05_AP_ZeroSlot_radio_address_000000.md)
went where it differed from the plan; its pull request is #241.

1. **The C line at 000000 could not be read.**
   Its 207 bytes are too few for a configuration of the Cube's own type,
   which needs 238, so `serve` logged it as a bad message and dropped it.
   That is why the proxy never repeated it.
   "Kept as received" became: a C line the snapshot cannot read is kept
   as the Cube sent it, one per address, until the next greeting
   (`cubelan.ErrKeptAsReceived`).
   `Lines` repeats it for the proxy and backups, and `SnapshotOf` reads a
   backup holding it.
2. **One guard instead of every builder.**
   The command builders keep their signatures.
   `cube.CheckZero`, called where every command leaves for the Cube
   (`Client.send`), refuses what addresses 000000 as a device;
   the API's `deviceOf` answers 400 before anything is queued.
   A room's radio command, which may carry 000000 with the room flag, passes.
3. **A client of the proxy** that sends a command to 000000, as the
   original software would for the entry's removal, gets no answer:
   the proxy logs "proxy: command failed" and the client times out.
   Clearing the entry stays the owner's, with `serve` stopped.
4. **The tests' lines** have the shape seen on the owner's Cube;
   the C line's other bytes are zero, since the Cube's were not recorded.
   `tools/identifiers/allowed.txt` names 000000 as no device's.
5. **Block 3** carries no CHANGELOG bullet: it changes documents only,
   and Blocks 1 and 2 carry one each.
6. **Verification**: `go test ./...`, `make race`, `make cross`, `gofmt`,
   the three `go vet` and `GUIDELINES/shared/tools/check` passed.
   Nothing was sent to a real Cube. On the owner's word, still to check:
   the entry gone from "Devices without a room", one warning per greeting
   in `serve`'s log, and the original software through the proxy.
