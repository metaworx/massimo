# NOTE UiParts v1.0: how Block 2 went

Where Block 2, Toolchain, went differently from the plan, a decision
taken at its gate, and what verified it.

## What it made

The page loads one more script, `ui/parts.js`: a bundle that `make ui`
builds from TypeScript under `internal/server/ui/src/` with esbuild run
from Go, with Preact vendored under `third_party/preact/`. It holds no
part yet, and registers an empty `window.MassimoParts`.
`make ui-check` type-checks the sources; the contract's "The web UI"
says how a region is written from now on.

## A decision at the gate

**D175-A, the guidelines' TypeScript baseline** (the owner, 2026-11-15).
Declaring TypeScript among the project's languages brings
`GUIDELINES/shared/lang/ts/` in. The project keeps to it where it costs
nothing and says the rest in its contract:

- a file under `ui/src/` opens with the SPDX and copyright lines, then
  the baseline's `@file` header;
- `make ui-check` is the parts' lint and `make ui-test` their test;
- the baseline's unit-test runner is not taken.

## Different from the plan

1. **Who did it.**
   A sub-agent on Opus 5.5 did the block without a commit, each step
   recorded as a tree; the commits were made from the trees after the
   commit gate.
2. **The bundler is a Go program of its own,** not a pinned tool run
   with flags: it finds the repository above it, takes no arguments,
   resolves the five Preact modules to the vendored files and refuses
   any other package. The published files carry no licence comment, so
   it adds one per package to the bundle.
3. **The Homebrew formula builds the bundle only where the archive has
   `tools/uibundle`:** a rolling formula can follow a release from
   before this block.
4. **CI's shared step writes `make ui`'s command out,** since the UI
   test's Playwright image has no `make`. The job UI types uses the
   runner's own Node.js, so no action is pinned for it.
5. **Beyond the plan's list:**
   - `GUIDELINES/config.ini` declares TypeScript;
   - `README.md` and the site's page are rendered again from the build
     fragment, which now says to bundle first;
   - `.gitattributes` fixes the vendored files' line endings, so that
     the bundle is the same on every checkout;
   - a pull request's UI tests also run for a change to
     `tools/uibundle/` or `third_party/preact/`;
   - `store-bench` depends on `make ui` too, as every target that
     compiles Go does.
6. **Main had cut a release** (v0.16.0-alpha.1) between the two blocks.
   The merge of main was clean, and the merged tree differs from main
   by this block's files alone.

## What verified it

- **Before the commits,** by the sub-agent: without the bundle
  `go build` stops and names `parts.js`; the bundle built twice is the
  same; `go test ./...`, `make race`, `go vet` on three platforms,
  `make cross`, `make actionlint`; `make ui-check`, which named a
  planted mistake; 70 runs of the UI suite; in a browser the page has
  `MassimoParts`, no console error and no violation of its security
  policy.
- **After the merge of main:** `make ui`, gofmt, `go vet` on three
  platforms, `go test ./...` (26 packages), `make cross`,
  `make actionlint`, `make ui-check`, the cut's `--check` and the
  guidelines' twelve checks pass.
- **Not run here:** the whole UI suite, which CI runs on the pull
  request.
- **Not verifiable here:** the workflows themselves (the shared step on
  the Windows and macOS runners, the job UI types, `build.yml`),
  Dependabot's reading of its two new entries, and the Homebrew build,
  which CI's macOS job makes. The pull request's own run is their
  first test.

## For every session, once the block is on main

A checkout needs `make ui`, or any `make` target that compiles Go,
before `go build`, `go test` or `go vet`: the bundle is embedded and
not committed.
