# NOTE UiParts v1.0: how block 12 went

Where Block 12, Maintenance, went differently from the plan,
the choices taken in the run, and what verified it.

**Block 12 was built before Block 11.**
The log's block waits for AP LogCursor's change to `log.js`,
its pull request #388, which was open;
so the log, `log.js` and the log's sign are still plain.

## What it made

- **`ui/src/software/`:**
  Maintenance → Software update as a part:
  the channel, Check, Update with its question, the helper's reading.
- **`ui/src/maintenance/`:**
  Maintenance → Maintenance as a part:
  the restart and the reboot with their questions, the delay, the cancel,
  the following while the server is away;
  the announcement and the intervals, saved at once.
- **`ui/src/sysinfo/`:**
  System info as a part:
  its facts, the store's and the settings' folds,
  the certificate's readings, the clock, the copies.
- **Plain:**
  `maintenance.js` and `system-info.js` are gone;
  `update.js` keeps `loadUpdate`, `updateOut` and `updateLatest`,
  which the header and the server's sign call,
  and the new `serverEvent`, each a call of the parts;
  `app.js` hands the stream's remaining kinds and its `resync` to `serverEvent`.
- **`ui/src/shared/` gained:**
  - `burst.ts`, `burstReader`:
    one read in flight and at most one after it,
    the page looked at as each starts;
  - `useAsk(held?)`, whether a question is open may live in a store,
    with its `box` and `Question`'s `boxRef`:
    the focus goes back to the button that asked
    only where it was inside the question as it went;
  - `NumberField`'s `inputMode`; Field's and Select's `labelCls` and `hintId`;
  - `Fold`'s `id`; `Copy`'s `name` and `CopyPair`; `CountList`.
- **`ui/src/model/event.ts`:**
  `ServerEvent` and `settingsChanged`.
- **`MassimoParts.signedOut()`** ends the helper's reading,
  the following of a restart or a reboot,
  the certificate's readings and the clock,
  takes the three questions back, sets the delay typed back to 60,
  and forgets the settings, the rows and System info's facts;
  the update's versions stay (D200).
- **No marks:**
  no section has a form with a Save, so none gets a pill (UnsavedMarks D6-A),
  and there is no `Added` fragment.
- **Without a caller now:**
  `noticeEl`, `linkEl`, `kvList` and `countList` of `components.js`,
  marked for Block 15 (D181-A).
- **Tests:**
  `test_maint_updates.py`, new;
  the guard's data sources per region and its three views;
  `test_update.py`, `test_server_sign.py`, `test_restart.py`, `test_reboot.py`,
  `test_settings_copy.py`, `test_cube_intervals.py`, `test_system_info.py`
  and `test_copy.py` brought to the parts.

## Events and reads

As built, and in `docs/ui.md`.
A page not shown reads nothing; showing it reads everything, as before.

| Section | Event | What it reads |
|---|---|---|
| Software update | `resync` | GET update, then GET settings |
| Software update | `change` of the setting `update.channel` | GET update, then GET settings |
| Software update | `update` from another browser, less than a minute old | takes Update's question back and starts the helper's reading with 30 s of grace; an older one reads the versions once |
| Maintenance | `resync` | settings, restart, reboot |
| Maintenance | `change` of `announce` or an interval | GET settings |
| Maintenance | `reboot`, `reboot_cancelled` | GET reboot |
| Maintenance | `settings_read` | nothing: the event names what waits |
| Maintenance | `restart` | nothing |
| System info | `resync` | facts, store and config |
| System info | `settings_read` | store and config |
| System info | `change` of `cube.add`, `cube.update`, `cube.remove` | facts |

How the flows and the events' reads are kept apart:

- **The update:**
  while this page's own update runs, its POST or its reading,
  an event reads no versions.
- **The restart and the reboot:**
  their rows are not read while the page follows them;
  a waiting reboot keeps its timer through a read that finds the same time.
- **The certificate:**
  an event's read of System info leaves the certificate's readings alone.
  After a restart they start again from 0
  where the `resync`'s read finds the certificate pending and nothing reading.
- **The page's own request:**
  an event's read of the channel, the settings or the reboot
  is not made while the page's own request for it is under way,
  but once, when that request has ended,
  and its answer shows nothing where a choice was made since.
- **Two regions do not share their reads:**
  one `resync` reads the settings twice,
  once for the channel and once for Maintenance's card,
  as showing Maintenance does.

## Different from the plan

1. **Who did it.**
   A sub-agent on Opus 5.5 wrote it in the session's own worktree,
   without a commit.
   Two independent readers on Opus read its recorded tree through git
   while the builder went on,
   one the software update and Maintenance,
   line for line against the plain code,
   the other System info, the shared parts, the OpenAPI file,
   the guard and the trees,
   and then checked each rework.
   Four rounds:
   the first hand-back kept the plain page's reads;
   the task to follow the stream came with the readers' 17 points;
   a second rework of 12 points followed, a third of 7,
   and a last, narrow check found no must left.
   The commits were made from recorded trees.
2. **Three steps, not one commit:**
   the plan names one,
   "fix(ui): Maintenance and System info follow the server while shown";
   the block is a commit per section,
   Software update, Maintenance and System info,
   each with its CHANGELOG fragment.
3. **The following of the server came in the rework,**
   not the first hand-back,
   which kept the plain page's reads and proposed a later block (D198).
4. **`server_started` and `update_result` never reach a page:**
   both are written at the server's start, before any stream is open,
   and a stream opened again across a restart gets `resync`, no replay.
   The first rework read on them; the readers found it;
   the sections read at the `resync` instead.
5. **An `update` event from another browser starts the reading**
   with the 30 s of grace `runUpdate` keeps after its own POST:
   a page that did not ask shows the buttons off and the helper's line,
   without the "requested" line, rides out the restart
   and ends when the helper says done or after 5 minutes.
6. **The helper's reading is a chain:**
   3 s after each answer, one at a time,
   the 5 minutes looked at before each.
   It was a fixed 3 s interval,
   which piled reads up while a sign-in was open after a 401;
   the plain page had that.
7. **The channel's busy part is the PUT alone:**
   the release check and the setting's read follow outside it,
   a later choice's reads replacing an earlier one's.
   The select is no longer off while it saves,
   and a second choice during the first one's check is taken.
8. **The line after Update names the version the server's answer gives**
   (`requested`): the POST carries no version,
   and the server installs its own latest.
9. **Selects and switches saved at once are not off while they save**
   (`useSetAtOnce`), so the focus stays; the plain page turned them off.
10. **Markup:**
    the reboot's delay row is not drawn while a reboot is not offered;
    it was hidden in place, and its id is gone.
11. **Required in the OpenAPI file, D177-A:**
    the fields the server always sends of UpdateInfo, UpdateStatus, Setting,
    StoreInfo, ConfigView and its variables;
    `GET /api/v1/system`'s answer is the named schema `SystemInfo`.
12. **The guard** got data sources per region:
    the header's update check;
    the page shown again, which waits until the page's requests have answered
    and fails a round that did not settle;
    the stream's events.
    It got two views, Update asking and the restart asking with a delay typed.
    System info's view fails on the page before the change;
    the other two and the events' source are forward guards.

## What the second reading found

Three rounds of rework, of 17, 12 and 7 points,
and a last check that found no must left.
The must points, and what a user would have met:

1. **A session-end test of System info** could pass before the late answer came;
   the first reading's only must.
2. **`server_started` and `update_result`** never reached a page (4 above).
3. **`useAsk` took the focus whenever it was on the body,**
   also from a user who had clicked on plain text,
   and changed what `done(false)` did for the questions of the blocks before
   (`rooms/Unlisted.tsx`, `rooms/ConfigDevices.tsx`):
   now only where the focus was inside the question as it went.
4. **The page's own PUT of a setting came back as a `change` event**
   whose reads ran outside the guard of the newer choice.
5. **A second choice of the channel was dropped without a word**
   during the first one's release check.
6. **The focus fell to the body** when a question was taken back.
7. **Tests that could not fail** for the fault they named, six of them,
   and tests of the plain code that had waited for a control to be on again
   and raced once nothing was off any more.
8. **In the third reading:**
   - a question of Update was left open
     when another browser's `update` event started the reading:
     Yes in the first 3 s was refused with 409
     and turned the buttons on for the whole install;
   - after a restart System info's certificate line stuck on "being read…"
     with nothing reading it.

The reader of the software update and Maintenance compared every request,
order, condition and timer of the update, the restart and the reboot
with the plain code at each reading,
and found them the same, but for the chain of 6 above.

## Seen and left

The readers' notes of the last check, none a must:

- **A Yes in the same turn as another browser's `update` event:**
  the event counts as this page's own;
  the POST gets 409, "not started" shows, the buttons are on,
  and the other browser's update is followed only from the next read,
  the header's check or Maintenance shown again.
  The server refuses a second update, so nothing harmful follows.
- **The channel's remembered read,**
  an event skipped during its own change, has no test of its own;
  Maintenance's settings case has.
- **`channelMissed` and `owns.*.missed` are not reset at a sign-out:**
  at most one read of the next user's own data, while the page is shown.
- **`serverSkew`** is declared in `src/plain/app.d.ts`; `header.js` defines it.
- **The guard's `change.cube` entry** is already in the first two steps' trees,
  though only System info, the third, uses it.
- **A timer's certificate reading from before a sign-out**
  can clear the flag of the next user's reading in flight:
  at most one overlapping request.
- **A change this page makes** comes back as its own event
  and is read once more after the change has ended.

## Decisions

Taken in the run under the owner's `EXEC++`, each the owner's to change:

- **D198.**
  Software update, Maintenance and System info read again on the stream's events
  while their page is shown, in this block:
  the plan's summary of Block 12 is "follow the server while shown".
  The other way: the plain page's reads alone,
  on showing the page, the user's actions and the header's check,
  as first built.
- **D199.**
  A question of Update, Restart or Reboot goes when what it asked about changed:
  a check finds another release;
  the restart or the reboot is no longer offered; a reboot already waits.
  The plain page kept it.
- **D200.**
  The update's versions stay across a sign-out:
  they are no user's data, every user may read them,
  and the server's sign needs them.
  The other way: forget them too;
  the sign then waits up to half an hour.
- **D201.**
  A page that did not ask follows another browser's update (5 above),
  only for an `update` event less than a minute old,
  the event's time against the browser's clock corrected by the server's;
  Update's question is taken back;
  busy follows what the reading finds;
  a POST of this page refused meanwhile leaves the buttons off.
  The other way: one read,
  which mostly finds the helper's last state and shows nothing of the progress.
- **D202.**
  The plain `serverEvent` lives in `update.js`,
  calling `MassimoParts.serverEvent`,
  since Maintenance and System info have no plain script left;
  Block 14 may move it with `app.js`.

## For the blocks still to come

- **An event that is written before a stream can be open never reaches a page:**
  read the server's code for when a kind is sent before a part is made to react to it;
  what a restart changed is read at the stream's `resync`.
- **A page's own request comes back as an event:**
  an event's read of a thing is dropped while the page's own request for it is under way.
- **`burstReader`** for a region that reads again on events.
- **`useAsk`:**
  a store may hold whether a question is open (`held`);
  the caller hands the question's box (`box`, `boxRef`).
- **A builder's own wait loop** (`until ! pgrep …`) matched its own command line,
  never ended, and had its hand-backs refused:
  a run is waited for through its notification.
- **Readers can read a recorded tree through git**
  while the builder goes on in the working tree.
- **Block 14** (`pages.js`, `app.js`' shell):
  `serverEvent` and the `resync`'s hand-over live in plain scripts until then.
