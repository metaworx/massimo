# NOTE LogEdges v1.0: how the run went

Where Blocks 1 to 3 went differently from the plan, what verified them,
and what the run found beside them.
The three blocks are one pull request, #400, a commit each,
with `main` merged in before it.

## The order

Block 3 was built first, while the owner asked why not D3-B and D5-B;
it depends on neither.
The owner answered "Keep A", and asked for a section
"Future improvements" in `docs/store.md` (Block 1).
Blocks 1 and 2 followed in order.

## Block 3, Test

1. **Beyond the plan, the room's state:**
   with the late flag turned off, the plan's own fault, the reading on
   failed the test 95 runs in 96; the one pass was a race between the
   follow-up loop and the re-send's own write.
   The second reader proposed a check that the room says `unconfirmed`
   after the re-send's report; with it, each of the three faults fails it
   10 runs in 10.
   The analysis's "caught all three planted faults" was not quite so.
2. **The time:** 0.92 → 1.25 s, since it waits out the re-send's deadline.

## Block 1, Store

1. **The owner's section:** `docs/store.md` section 11,
   "Future improvements", with `AUTOINCREMENT` for `log.id` at the next
   migration that rebuilds `log`, and why it waits.
2. **`TestEventsPrunePlan`, beyond the plan:**
   the prune had no check of its index; off it, SQLite takes `log_cube`
   and the last, empty chunk reads all of a Cube's rows.
   The walk moved into `pruneWalk` so that a test reads the statement.
3. **`TestEventsPruned` changed:** with the fix, its second old row was the
   log's newest, which goes only at a second prune, and whether two
   requests made two was timing; one newer line makes one enough.
4. **The same case in three more places:** the OpenAPI file's
   `LogCursorBeyond`, `docs/ui.md`, and a line of `docs/api-v1.md`.
5. **The second reader's points, fixed before the commit:**
   two new tests read the log before the writer's timer wrote the prune's
   own line, which a pause of over 1 s showed; they flush and count it.
   No test told the newest by id from the newest by time; a row's time
   now does.
6. **What it does to the 409**, as told to session "UI refactor":
   the log emptied by the prune is no longer one of its cases;
   the log's part needs no change.

## Block 2, Reload

1. **The warning is the `settings_read` event's**, beyond the plan's
   "a Warn line beside the Info line":
   the reloader's own log reaches stderr and the log file only,
   never the log the warning sign reads.
   `LogSettingsRead` takes what the next start refuses, and the line is at
   warn with the start's own error after "the next start refuses:",
   as `log_rotated` is.
2. **A settle rule, beyond the plan:** a later `settings_read` below warn,
   or `server_started`, settles it, so that the sign goes out once the file
   is right.
3. **One line, on the second reader's point:** the reloader's own Warn line
   went, since the event's line names the setting and the error.
4. **Fixed values:** a value given by a flag of `serve`, by the global
   `-log-level` or by the process environment never warns:
   the start never reads it from the file.

## Found, not changed

1. The start refuses more settings than the four Block 2 checks,
   which a reload still takes without a word:
   `MASSIMO_LOG_ROTATE_SIZE`, `MASSIMO_LOG_KEEP`, `MASSIMO_LOG_KEEP_MIN`,
   `MASSIMO_HSTS`, `MASSIMO_TRUSTED_PROXIES`, `MASSIMO_RESTART`,
   `MASSIMO_SIGHUP`, `MASSIMO_ANNOUNCE`, and the TLS settings;
   each is one more entry in `startChecks`.
2. The reboot switch's warning at a reload reaches stderr and the log file
   only, so the warning sign never counts it.
3. `audit.id` has no `AUTOINCREMENT` either, and its prune can empty the
   table; its ids are only a `before=` cursor, with no marks on them.
4. `resend_test.go` still shows with a fixed 200 ms that no re-send follows
   a proxy write; nothing follows that report to read on to.

## Verification

Each block: a builder, an independent second reader whose points were fixed
before the commit, faults planted for each new or changed test
(six for Block 1, eight for Block 2, three for Block 3),
`-race` at scale 2, `gofmt`, `go vet` for the three systems,
`go test ./...` after the merge of `main`, the guidelines check;
the pull request's run green at its first attempt, in 9 minutes.
