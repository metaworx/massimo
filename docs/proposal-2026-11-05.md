## 2. Colour schemes in the web UI

What the owner wants: several schemes to choose from in Settings, a
custom scheme the user edits, saved in the browser, exportable.

What the code offers: the colours are 19 tokens on `:root` in
style.css (`--bg`, `--fg`, `--muted`, `--card`, `--card-head`,
`--line`, `--accent`, `--accent-fg`, `--heat`, `--ok`, `--warn`,
`--bad`, `--notice-bg`, `--notice-fg`, `--fill-ok`, `--fill-warn`,
`--fill-bad`, `--fill-info`, `--fill-fg`), with a dark set under
`prefers-color-scheme` and `:root[data-theme="dark"]` /
`:root:not([data-theme="light"])`, which the CSS already honours but
no script sets. Outside the token blocks only three `rgba()` shadows
are hard-coded, and config.js sets `--warm` for the programme bars.
The feature is therefore mostly settings and a small editor, not a
restyling.

Design:

- Settings → Appearance: **Mode** (system, light, dark; sets
  `data-theme` on `<html>`, stored as `massimo.theme`) and **Scheme**
  (the built-in ones and the user's own; stored as `massimo.scheme`).
  Mode and scheme are separate: a scheme carries a light and a dark
  set, the mode picks which is applied.
- Built-in schemes: the current one stays the default; two or three
  more (for example high contrast, and one without the blue accent
  for people who find it strong). The owner picks the set.
- **Customise…**: a panel with one colour input per token, for the
  light and the dark set, applied live; a contrast hint next to the
  pairs that must stay readable (`fg`/`bg`, `accent-fg`/`accent`,
  `fill-fg`/`fill-*`, `notice-fg`/`notice-bg`, WCAG ratio); Save as
  (name), Delete, Reset to the built-in it started from. Custom
  schemes live in `massimo.schemes` (JSON).
- **Export** downloads the scheme as JSON; **Import** reads one. The
  format is the document a server will later store per user, so it
  is fixed now:

  ```json
  {"format": "massimo-scheme/1", "name": "Mine",
   "light": {"bg": "#f6f6f4", "fg": "#1c1c1a", "...": "..."},
   "dark":  {"bg": "#151514", "...": "..."}}
  ```

  Token names without `--`; a missing token falls back to the
  built-in default; unknown tokens are ignored.
- Applied with `style.setProperty` on `<html>` (CSSOM is not blocked
  by the page's `Content-Security-Policy`; a generated `<style>`
  element would be). The download uses a `blob:` URL with the
  `download` attribute; the smoke test confirms both under the CSP.
- Texts through i18n.js in one `appearance.*` block, the four machine
  translations marked as the others; docs/ui.md gets a paragraph;
  smoke.py gets checks (a scheme changes the computed `--bg`, export
  produces the JSON, import round-trips, 390 px).

Later, with users (section 4): `GET/PUT /api/v1/me/preferences`
stores the same document per user; the browser copy becomes the
cache and the fallback when nobody is logged in. The other settings
(poll, expert, clock, language) move the same way.

## 3. Backup and restore in the web UI

Backup exists in the API (`GET …/backup?format=yaml|json`); the UI
has no button. Restore exists only as the command `massimo restore`
(plan, show, confirm, send) on top of `backup.NewPlan` and
`Plan.Run` through `cubeio.Writer`.

API, following the command's dry-run-then-send shape:

- `POST /api/v1/cubes/{sn}/restore/plan`: body is the backup file
  (JSON or YAML by `Content-Type`), options as query parameters like
  the command's flags (`portal`, `state`, `skip=names,settings,…`).
  Answer: the steps (`what`, whether it is a radio command, device and
  room), the notes (devices to pair again), the number of radio
  commands, the duty-cycle cost (about 1.25 % per radio write, from
  the hardware day), the current budget, and a hash of the plan.
- `POST /api/v1/cubes/{sn}/restore`: same body and options plus the
  plan hash; answers 202 with a restore id and runs the steps through
  the queue at low priority. Progress as `restore_step` events on the
  stream, the whole state at `GET …/restore` (running, done, failed;
  each step's result). Refused when a restore is running, the Cube is
  not connected, the backup's serial is not the Cube's, the duty
  cycle is above 80 % (the threshold of the write test), the body is
  over 1 MB, or the plan hash no longer matches the Cube's state.
- Hidden devices are protected by `PlanOptions.Hidden` as in the
  command; `-show-hidden` on `serve` maps to `ShowHidden`. `state` and
  `portal` stay off by default.
- Tests against the fake Cube in the project's standard: an edited
  backup gives exactly the expected steps, the run sends exactly the
  expected lines. docs/api-v1.md and the OpenAPI file get the routes
  (`TestOpenAPICoversRoutes` enforces it).

UI: Settings → Backup and restore. **Download backup** (YAML or JSON;
fetched with the token and saved through a `blob:` link, since a
plain link cannot carry the bearer token). **Restore from file…**:
file picker, the plan as a table with the notes and the cost, the
groups as switches, then **Send N commands**, a progress list, the
result. The panel reminds the user to download a backup first until
the server keeps backups itself.

With storage (section 4): automatic backups (at each connect, daily,
before every restore), a list with download, restore from a stored
backup without upload, and a difference view between two backups.

## 4. Persistent storage for `serve`

The owner's view, which this proposal shares: a store is the next
foundation. Today everything the server knows beyond the Cube's own
data is in `.env` (read once, needs a restart) or in memory (the last
500 events, the Cubes found by discovery, pairing results, the
lockout counters), and the UI's settings are per browser. The
features in the queue need it: settings editable in the UI (hidden
devices, Cube names, the stale threshold), found Cubes that stay
found, a log that survives a restart, backup history, users with
roles, and preferences per user such as the colour scheme.

Standing decision of the owner (handover, "Open decisions"): a design
document first, then decisions, then code. Proposed content of
docs/store.md:

1. **Engine.** SQLite through `modernc.org/sqlite` (pure Go, so `make
   cross` keeps building every target on one machine without C
   toolchains; design.md names SQLite for standalone and edge, and the
   same SQL carries to PostgreSQL in server mode). Cost: a large
   dependency tree against today's two, and a few megabytes more per
   binary; govulncheck in CI covers it. The lean alternative is
   `etcd-io/bbolt` (one small package, key-value, no queries) with the
   log and the backups as files; it serves settings, users and
   preferences well and the log poorly. Either sits behind
   `internal/store` with a small interface, so the choice can change.
   A JSON state file is enough for preferences but not for a log, a
   history or several users, so it is not proposed.
2. **Location.** One file, `massimo.db`, in the state directory the
   installers already create: `/var/lib/massimo` on Linux and macOS
   (the service user's home), `%ProgramData%\Massimo` on Windows,
   `./massimo.db` or `-data <dir>` for a terminal run.
3. **What moves from `.env`, what stays.** Stays (bootstrap and
   secrets): the listen address, the log file, the API token, the
   Cube keys and IVs, the data directory. Moves: Cube names,
   addresses, proxy addresses and serials, hidden lists, the
   discovered Cubes, plus everything new. On the first start with an
   empty store the Cube entries are seeded from `.env`; afterwards the
   store is the truth for those and the UI edits them, while the
   `.env` lines are still read as a fallback for a Cube the store does
   not know, with a log line saying so. Secrets encrypted at rest can
   come later; keeping them in the file keeps the first version
   small.
4. **Schema, first version.** `schema_version`; `settings` (key,
   value, updated); `cubes` (serial, name, address, follow discovery,
   proxy address, proxy serial, hidden list); `users` (name, argon2id
   hash, role, disabled); `tokens` (user, hash, kind: browser session
   or API key, expiry, last use); `preferences` (user, key, JSON
   document); `events` (the log, retained for N days, replacing the
   ring of 500); `audit` (who did what, the `actor` of the #20 events
   made durable); `backups` (Cube, time, reason, format, bytes).
   `tenant_id` on the rows design.md section 6 asks for, defaulting to
   one tenant.
5. **Users.** Roles from design.md trimmed to standalone: owner,
   operator, viewer, integration. The first start without users
   creates the owner from `MASSIMO_API_TOKEN` (the token stays valid
   as the integration key, so the Pi and scripts keep working);
   `massimo user add` for the command line; login in the web UI with
   a browser session token; the lockout from #7 moves to the store.
   Per-Cube ownership arbitration (roadmap 6) is a column on `cubes`
   and a check in the write paths, in a later stage.
6. **The commands.** `status`, `backup`, `restore` and the others keep
   reading `.env` and talking to the Cube or the proxy; they do not
   open the store. A later `-server <url>` mode lets them use the API
   instead.
7. **Stages after the decision**, one pull request each: (a)
   `internal/store`, migrations, seeding, `cubes` and `settings`, the
   UI for Cube names and hidden devices; (b) users, login, tokens,
   audit; (c) preferences and the scheme sync; (d) the log in the
   store with retention; (e) backup history (section 3).

## 5. Installation section in the README

The README builds from source and points at packaging/README.md in
one sentence; packaging/README.md has everything (download or build,
the Pi, `massimo install`, by hand, networks, updating, Windows,
macOS) but a newcomer reads the README first. Proposed: a section
**Installing** right after the introduction, one subsection per
operating system (Linux including the Raspberry Pi, Windows, macOS),
each with **Try it** (download the release asset for the
architecture, check `SHA256SUMS`, put a `.env` next to it, `massimo
serve -listen …`, open the page) and **As a service** (`massimo
install …`, where the settings and the log then live, `massimo
update`, `massimo install -remove`), with links into
packaging/README.md for the details and a note on what WSL cannot do.
A documentation-only change in README.md, so it conflicts with
nothing.

## 6. Order and split into sessions

own worktree and its own files, a branch `claude/<topic>`, `main`
merged into the branch right before the pull request, roadmap and
handover edits in one small final commit, i18n keys in one block per
feature, `make ui-test` at 1100 and 390 px for every UI change (after
the Playwright venv is set up), `go test -race ./...` for core
changes. A coordinating session hands out the work and relays the
owner's decisions. Nothing that needs the proxy or discovery is
tested in WSL; that is the Pi's job.

## 7. Decisions for the owner

1. The storage engine: SQLite through `modernc.org/sqlite` (proposed)
   or bbolt with files.
2. Secrets stay in `.env` for the first storage version (proposed), or
   move encrypted into the store from the start.
3. Users in the first schema with the login in stage (b) (proposed),
   or users later.
4. The built-in colour schemes: which, how many; the default stays.
5. The restore guard rails: duty cycle above 80 % refuses, `state` and
   `portal` off by default, the serial must match.
6. Start S1 to S4 now in parallel, or in another order.
7. Carried over: real serials and room names in the docs; deleting
   the two stale remote branches; the `.env` correction on jaguar.
