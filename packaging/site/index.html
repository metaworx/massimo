Massimo

Open-source successor software for eQ-3 MAX! heating systems (the MAX! Cube LAN gateway, radiator and wall thermostats, window contacts, eco switches) after the vendor's end of life.

One program, massimo serve, on a small box on the Cubes' network (a Raspberry Pi 1 is enough) gives them a web UI for phone and desktop, a JSON API, and a proxy through which the original MAX! software keeps working. It runs on your own hardware, with no account and no cloud. Massimo is in early development: every release is a pre-release on the update channel alpha.

Install

A binary is only as trustworthy as the place it came from. Massimo runs as a service on your network and controls your heating, so take it from the project's releases, its apt repository or its Homebrew tap, and never from a copy elsewhere: a mirror, a forum post or a prepared image may carry a changed binary, and no check of the project's can tell. SHA256SUMS proves that a download arrived as the release has it, not who built it: it sits on the same page as the binaries, and whoever could replace one could replace the other. Once a binary runs, massimo update checks every later release against the release key compiled into it, and apt against the repository's key, so what is left to trust is the first install. To trust no build but your own, build it from the signed source: From source.

Debian, Ubuntu, Raspberry Pi OS: the apt repository

One suite per update channel: {{SUITES}}. Install the keyring package first, then the sources:

curl -fsSLo /tmp/massimo-archive-keyring.deb https://massimo.metaworx.ch/apt/massimo-archive-keyring.deb
sudo apt install /tmp/massimo-archive-keyring.deb
sudo tee /etc/apt/sources.list.d/massimo.sources <<'EOF'
Types: deb
URIs: https://massimo.metaworx.ch/apt
Suites: alpha
Components: main
Signed-By: /usr/share/keyrings/massimo-archive-keyring.gpg
EOF
sudo apt update && sudo apt install massimo

Then create the first owner and start the service, see The first settings; sudo apt upgrade installs each release from then on and restarts the service. A single release's package is also on the releases page: _arm64.deb for a 64-bit Raspberry Pi OS, _armhf for a 32-bit one (the Pi 1 included), _amd64 for a PC. The repository's key, for a check by hand, is massimo.asc. A box that followed the old address https://metaworx.github.io/massimo/apt changes its sources once: Moving from the old address. Details: The apt repository.

macOS: Homebrew

brew install metaworx/massimo/massimo-alpha
brew services start massimo-alpha

Homebrew builds the release from source. The settings are in $(brew --prefix)/etc/massimo/env, and brew upgrade massimo-alpha updates it. Details: Homebrew.

Windows: the service

Download massimo-windows-amd64.exe from the releases page. Then, in PowerShell opened with "Run as administrator", in that folder, with a settings file .env next to it (an empty one will do, see The first settings):

.\massimo-windows-amd64.exe install -dry-run -settings .env
.\massimo-windows-amd64.exe install -settings .env

This installs the service massimo and its firewall rule; the web UI's button and massimo update install the next release. The binary is not code-signed: one downloaded with a browser meets SmartScreen's "Unknown publisher" when started from Explorer. Details: Windows.

Linux and macOS: the binary as a service

Every release carries one binary per platform, with SHA256SUMS and a signed manifest, on the releases page; Installing says which binary fits which box. As root, in the folder with the binary (here the one for a 64-bit Raspberry Pi) and a settings file .env (an empty one will do, see The first settings):

chmod +x massimo-linux-arm64
sudo ./massimo-linux-arm64 install -dry-run -settings .env
sudo ./massimo-linux-arm64 install -settings .env

This installs a systemd service on Linux, a LaunchDaemon on a Mac; the web UI's button and massimo update install the next release. Details: Install with massimo install.

From source

Every release can be built from its signed tag, with git, make and Go 1.26 or later (https://go.dev/dl/):

git clone https://github.com/metaworx/massimo.git
cd massimo
git -c gpg.ssh.allowedSignersFile=/dev/null verify-tag <tag>
git checkout <tag>
make

verify-tag checks the tag's signature. With no signer it trusts (/dev/null), git prints the key's fingerprint, then No principal matched., and exits 1; the fingerprint must be SHA256:R3Ihevc2jMppLJtKIhmpfRmulpf7DXuWBFbCjaU3qcs, which the guidelines' README names as well, under "Verifying a release", https://gitlab.com/metaworx/open-source/mwx-guidelines, on a host this repository does not control. The key itself is deliberately not given here: whoever could change the tags could change the line naming it.

make runs the tests and builds ./massimo for this machine, make build without the tests; make linux-armv6 builds for a Raspberry Pi 1, make linux-arm64 for a 64-bit Raspberry Pi OS, make windows for Windows, and make cross every release binary, all into dist/. The binary goes in as a release's does, sudo ./massimo install -dry-run -settings .env, then without -dry-run. It follows the tag's update channel, so the web UI and massimo update say when a release is out, and they install the project's binary, checked against its signed manifest; to stay on your own builds, build the next tag and run install again, which replaces the binary and keeps the settings. A tag up to v0.12.0-alpha.1 follows HEAD instead, which has no releases, unless built with make CHANNEL=alpha.

The first settings

On the Cubes' LAN the server needs no settings to begin with: while there are no users, the web UI, http://<the box>:8099/, offers the local network a form for the first owner, and System settings → Cubes lists the Cubes the server finds, each added with Add. The settings take what discovery and the web UI cannot give: the address of a Cube that discovery does not reach, on another subnet or behind a VPN (massimo discover lists the Cubes it hears, with serial and address), and a token that becomes the owner's key at the first start, which the API and the web UI then ask for, so that no form for the first owner is open on the LAN:

MASSIMO_CUBE_KEQ0000000_ADDRESS=192.168.1.10
MASSIMO_API_TOKEN=choose-a-long-random-string

A Cube takes one client at a time: close the original MAX! software first; from then on that software connects to the server's proxy.

The Debian package leaves a new box stopped, since until it has an owner every device on the local network may use it. Create the owner on the box with sudo -u _massimo /usr/bin/massimo -env /etc/massimo/env -data /var/lib/massimo user add <name> -role owner, or put the token into /etc/massimo/env, or create the owner in the web UI once the service runs; sudo systemctl start massimo starts it, and from then on every upgrade restarts it. massimo install -settings .env starts the service with that file, an empty one too. Details: Server.
